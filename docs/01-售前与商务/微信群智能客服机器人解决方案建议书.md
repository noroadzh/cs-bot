## 一、项目背景与需求理解

建设一个智能客服机器人：对接微信、加入微信群回答客户疑问、7×24 监控群消息并及时应答；技术路线为「大模型个人助理 + RAG 知识库 + 自动学习」。

**核心价值主张**：把 60%–80% 的重复咨询交给 AI，人工只处理高价值对话，7×24 秒级响应，且客户资产留在合规通道里。

**目标客户画像**（满足 3 条以上即为高潜）：微信群 ≥10 个、日咨询 ≥100 条、人工客服 ≥2 人、问题重复率 ≥50%。典型行业：电商/私域运营、教培/知识付费、本地生活服务、品牌代理商体系、中小企业售后。

**痛点量化基线**：
- 人工客服 7×24 三班倒需 ≥4 人，年成本 35–45 万
- 响应超 5 分钟，私域咨询转化率下降 50%+
- 夜间（20:00–8:00）咨询占比 25%–40%，基本流失
- 群消息 60%–80% 为 FAQ 级重复问题；多群漏答率 20%–40%

**ROI 测算**（以 20 群、日咨询 500 条的中型私域商家为例）：AI 拦截 70% 重复问题后客服 3 人减至 1 人，年直接节省 16–21 万 + 增量转化 5–10 万；首年投入约 19–25 万，**回收期 6–12 个月，次年起年化 ROI >200%**。

## 二、关键合规前提（红线，必须先决策）

⚠️ **个人微信/微信群没有任何官方机器人 API**。市面"个人微信机器人"均为协议逆向/PC Hook 方案，属微信用户协议明令禁止行为：

| 维度 | 方案 A：企业微信官方 API（主推） | 方案 B：个人微信协议/Hook |
|---|---|---|
| 合规性 | 官方合规，可签合同验收 | 违反微信协议，封号风险真实高发 |
| 稳定性 | 官方 SLA，可持续运营 | 微信版本更新即可能失效 |
| 覆盖 | 企微客户群/外部群（微信用户可加入） | 任意微信群，但账号资产可能一夜清零 |
| 定位 | **正式交付路径** | 仅 ≤2 周概念验证，须客户书面风险确认+合同免责 |

**建议**：以企业微信官方 API 为交付基线；若客户必须覆盖原生微信群，引导迁移至「企微外部群」，或个微侧仅做"监听+人工草稿辅助"的 copilot 模式（不自动发消息）。

## 三、总体架构方案

### 3.1 分层架构

```
┌─────────────────────────────────────────────┐
│ 运营后台（AntD5 Web）                         │
│ 群管理/知识库/待学习池/对话记录/看板/设置        │
├─────────────────────────────────────────────┤
│ 对话引擎（LLM Agent）                          │
│ 上下文管理→意图识别→Agent编排→LLM生成→出站审核  │
├─────────────────────────────────────────────┤
│ RAG 检索层                                    │
│ Query改写→向量Top20+BM25混合→Rerank→置信度判断 │
├─────────────────────────────────────────────┤
│ 消息网关                                      │
│ webhook验签→去重幂等→限流→敏感预过滤→会话路由   │
├─────────────────────────────────────────────┤
│ 接入层：企业微信官方API适配器（抽象接口，可换通道） │
└─────────────────────────────────────────────┘
基础设施：PostgreSQL+pgvector / Redis / Docker Compose 单机部署
学习闭环：会话日志→未命中聚类→人工审核→版本化发布→回归评估
```

> 范围口径（v1.2 明确）：上图为**产品完整蓝图**。本期 MVP 的实际交付形态为——知识运营界面由**问答平台自带后台**承载（文档上传/切分/QA 补录/检索调试），管理类操作（未命中导出、素材管理、历史导入审核、授权与配置查询）以**管理接口 + 操作手册调用示例**交付；图中"运营后台"部分（统一可视化的独立运营后台）与**数据看板**归入二期（参考价见《MVP 报价单》第五节）。

### 3.2 关键技术选型

| 决策点 | 选型 | 理由 |
|---|---|---|
| 接入通道 | 企业微信官方 API | 合规红线，见第二章 |
| 大模型 | DeepSeek-V3 API（通义 fallback） | 10 群月成本仅 ¥300–500；架构留 LLM 抽象层可切自建 |
| 向量库 | pgvector | 与 PG 合一少组件，MVP 单机够用（<100 万向量无压力） |
| Embedding/Rerank | bge-m3 + bge-reranker-v2-m3（自部署） | 中文效果好、省 token、可控 |
| 检索策略 | 向量+BM25 混合 RRF 融合 + Rerank Top3 | 命中率保障 |
| 置信度 | 三级策略：高直接答 / 中带提示 / 低拒答转人工 | 杜绝幻觉硬答，拒答率 ≤20% 写入合同且不计缺陷 |
| 后端 | FastAPI + Celery/RQ；前端 Ant Design 5 | 成熟生态，人天成本最低 |

### 3.3 "自动学习"的正确落地方式（防污染是核心）

MVP **不做**在线微调、**不做**全自动入库。落地位 = 知识库持续运营闭环：

1. **采集**：全量会话日志（问题、命中、答案、👍👎、是否转人工）
2. **挖掘**：未命中/低置信/👎 问题每日离线聚类 → 候选 FAQ 清单（AI 建议答案草稿）
3. **人工审核（强制闸门）**：标注工作台人工确认/改写后才可发布——无人工审核不得入库
4. **版本化发布**：灰度群→全量群；每次发布快照，可一键回滚
5. **回归评估**：发布前自动跑 ≥100 条冻结评测集，命中率不低于基线 -2% 才放行
6. **可追溯**：prompt 模板与知识版本绑定，任何问题可定位到"哪个 prompt + 哪版知识"

### 3.4 可靠性设计

消息去重（msgid Redis SETNX 24h）、消费幂等状态机（崩溃重投不重复回复）、双维度限流（每群 20 条/分、每人 5 条/分）、按群分片队列（单群故障隔离）、LLM 超时 15s+重试+降级话术、通义 fallback 自动切换、监控告警（存活/失败率/延迟/积压）。

## 四、产品规划与 MVP 范围

### 4.1 范围裁剪

**P0（MVP，必须）**：企微接入+多群管理+消息去重；RAG 问答（三级置信度+来源引用+FAQ 精准匹配）；知识录入（PDF/Word/Excel 上传+自动切分索引，走问答平台自带后台）；未命中问题池+人工审核入库；转人工（卡片通知/代答/转派/15min 升级）；企微告警；安全基线 10 项。

**P1（二期，MVP 后 4–8 周）**：**独立运营后台（把管理接口统一可视化 + 角色权限）与数据看板**（本期管理操作为接口形态、知识运营用问答平台自带后台，见 3.1 范围口径）；图片 OCR/语音转写、知识版本管理+命中统计、日志聚类挖掘增强、👍👎反馈闭环、完整人工工作台、追问澄清、业务告警。

**P2（三期）**：多模态理解、自动评测回归、自助式 SaaS 平台（在线注册/自助开通/在线支付/按量计费）、主动营销、CRM/工单集成、私有化模型部署。（注：SaaS 托管形态本身已纳入本期可选能力，见 4.4；三期仅指自助化与在线计费）

**裁剪理由**：核心闭环是"听得见→答得准→答不了能兜底→能沉淀"，缺一环客户就感知不到"智能"；图片/语音等依赖真实数据积累，"全自动学习"风险最高改为半自动。

### 4.2 MVP 验收标准（可写入合同附件）

| 指标 | 标准 | 口径说明 |
|---|---|---|
| 响应时延 | P95 ≤ 8s | 连续 7 天线上日志 |
| FAQ 命中率 | ≥ 80% | 以双方签字冻结的评测集为准 |
| 答案正确率 | ≥ 90% | ≥100 条评测集回归 + 每月抽检 ≥100 条 |
| 拒答/转人工率 | ≤ 20% | 拒答属设计行为，不计入缺陷 |
| 系统可用性 | ≥ 99% | 剔除 LLM API 与微信平台侧故障 |
| 幂等 | 同 msgid 不重复回复 | 可现场演示 |

### 4.3 用户体验设计要点

- **群内交互**：@机器人触发（未被 @ 零噪音）；「引用+答案(≤200字)+来源引用+👍👎/转人工按钮」三段式回复；拒答话术友好且自动入学习池；免打扰时段+静默限流
- **待学习池三栏工作台**：聚类问题列表 → 原始上下文 → 标注表单（AI 建议答案草稿，Enter 发布下一条）；同组问题批量采纳
- **转人工**：值班人卡片含完整上下文（提问人/问题/机器人尝试答案/前后 5 条对话），可代答/跳转/转派；人工回复一键沉淀知识库（≤2 次点击）——学习闭环能否运转的体验关键

### 4.4 交付形态：私有化部署 与 SaaS 托管（两种可选）

同一套产品同时支持两种交付形态，客户按数据敏感度、运维能力与预算选择，功能完全一致，并支持后期迁移：

| 对比维度 | 私有化部署 | SaaS 托管 |
|---|---|---|
| 数据位置 | 部署在客户自有服务器，数据不出域 | 部署在交付方云上，每租户独立实例、数据归客户 |
| 隔离方式 | 单客户单实例 | 每租户独立实例/数据库/域名/密钥（物理隔离，非共享实例） |
| 运维责任 | 客户方运维，交付方提供手册与指导 | 交付方运维（监控/备份/升级/故障处理） |
| 付费方式 | 一次性开发费 + 年度维护费（15%） | 一次性开通实施费 + 按年订阅（标准档 ¥15,000/年、增强档 ¥28,000/年） |
| 上线时效 | 客户资源就绪后 25–43 个工作日 | 平台建成后每租户 ≤ 30 分钟开通 |
| 适用客户 | 数据敏感、已有服务器与运维能力的中大型客户 | 中小客户、自有资源紧张、希望快速上线免运维 |

- 合规底座一致：两种形态下租户/客户数据均归客户所有；SaaS 形态下交付方仅作为受托处理方（签数据处理协议），承诺不跨租户使用、不用于模型训练；提供数据导出与注销删除机制。
- 选择建议：业务数据涉及客户个人信息较多、有等保/审计要求的客户选私有化；初创或中小客户先用 SaaS 快速验证，规模上来后迁私有化。

## 五、安全与合规

### 5.1 合规要点

- **PIPL**：外部客户群机器人入群须自动发送《隐私告知》（采集目的/范围/留存/删除渠道）+群公告明示；非触发消息不存原文；敏感个人信息打码且不入学习库；LLM API 属委托处理，须选承诺不留存的服务商
- **等保**：单体应用建议按等保二级基线自查；政府/金融客户或敏感信息 ≥10 万条需评估升三级；定级责任在客户（系统运营者），写入合同
- **留存策略**：原始对话(含PII) ≤30 天加密 → 脱敏日志 6–12 个月自动清理；审计日志 ≥6 个月追加写

### 5.2 风险分级（Top 项）

| 风险 | 等级 | 处置 |
|---|---|---|
| 提示词注入泄露 prompt/知识库 | 高 | 输入规则拦截+输出特征检测+prompt 加固 |
| 出站违规内容企业担责 | 高 | 敏感词库+云内容安全机审两级闸口+兜底话术 |
| 知识库投毒 | 高 | 自动学习仅进候选池、强制人工审核、版本回滚 |
| API Key/企微 Secret 泄露 | 高 | .env 管理、轮换、仓库历史扫描 |
| 群成员信息无告知采集 | 高(外部群) | 入群隐私告知+最小化+脱敏 |
| 后台被攻破 | 高 | RBAC+2FA+IP 白名单+注入/XSS/CSRF 防护 |

### 5.3 MVP 安全基线（10 项强制）

回调验签防重放 / 出站两级内容审核 / 注入双侧检测 / 学习仅人工审核入库 / PII 入库前脱敏 / 密钥 .env+仓库扫描 / 后台强口令+IP 白名单 / 容器非 root 仅开 22(限IP)+443 / 入群隐私告知 / 审计日志+日志自动清理。

## 七、开发周期与交付计划

### 7.1 里程碑（基线 6 周 + 2 周试运行）

| 周 | 里程碑 | 关键交付物 | 质量门禁 |
|---|---|---|---|
| W1 | M1 需求冻结 | PRD 签字；**企微权限申请提交（D1 前）**；评测集初稿 | G1：PRD 签字+申请已提交 |
| W2 | M2 消息链路打通 | 验签/监听/@触发/去重/限流 Demo；**评测集冻结** | G2：Demo 演示+评测集书面冻结 |
| W3 | M3 RAG 联调 | 混合检索+rerank+三级置信度；首次跑分 | G3：命中率 ≥70%（试运行前须 ≥80%） |
| W4 | M4 后台+学习闭环 | 知识库后台/标注工作台/转人工/版本回滚 | G4：闭环全流程走通+15min 告警实测 |
| W5 | M5 安全达标+集成测试 | 安全 10 项核验；压测 P95≤8s；试运行评审 | G5：安全清单签字+压测达标 |
| W6 | M6 灰度启动 | 1–3 个群试点，日报跟踪 | G6：见下 |
| W7–W8 | 试运行观察+推广 | 观察期 2 周 → 50%→100% 推广 → 正式验收 | 命中率 ≥80%、正确率 ≥90%、无安全事件 |

**关键路径**：企微权限申请（W1 提交，外部依赖不可控，并行用测试企业号兜底）→ 消息链路 → RAG 联调 → 集成测试 → 灰度。

**团队配置**：2 后端 + 1 算法 + 1 前端 + PM 兼职（共 95 人天）。若需压缩至 4 周：学习闭环砍为最小版（仅未命中池+人工录入），需客户确认取舍。

### 7.2 Top 交付风险

| 风险 | 应对 |
|---|---|
| 企微权限申请周期不确定 | W1 D1 提交+测试号并行开发+客户指定 IT 对接人 |
| 知识库冷启动不足→命中率不达标 | W1 即收集客户历史客服语料；M3 <70% 升级协调；试运行专项补库 |
| 评测集确认拖延 | 合同明确 W2 冻结点；候选集客户勾选制；逾期书面函告 |
| 客户群形态与企微不匹配 | M1 实地核查群类型；不匹配走范围变更 |
| LLM API 稳定性 | 通义 fallback 自动切换；错误率 >5%/30min 触发切换 |

### 7.3 上线后 SLA 与运营节奏

- 缺陷分级：S1 致命 30min 响应/4h 恢复；S2 严重 2h/1 工作日；S3 一般 1 工作日/3 工作日
- 知识运营：试运行期每 2 天一轮标注发布；稳定期每周 1 轮+周报；每月知识库健康盘点；**客户须指定 1 名知识运营专员**（长期命中率的生命线）

## 八、结论与下一步行动

**结论**：方案技术可行、成本可控、合规路径明确。核心决策点是**放弃个人微信协议路线、走企业微信官方 API**——这是项目能否正式交付与长期运营的前提。

**下一步建议（按序）**：
1. 确认接入路线（企微官方 API / 个微过渡双轨），签署风险确认
2. 启动企微应用注册与接口权限申请（最耗时外部依赖，越早越好）
3. 收集历史客服语料/FAQ 文档，启动评测集共建（W2 前冻结）
4. 确认 MVP 范围（6 周基线 or 4 周压缩版）与预算（¥17–22 万）
5. 指定客户侧知识运营专员与值班客服排班
